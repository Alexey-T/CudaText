- REVISED: the whole search logic of the tree filter - it was still
  flawed after the previous live-update rework. What was wrong:
  while a search ran, results did not show in the tree at all (the
  tree stayed empty until the scan ended); cancelling the search left
  nothing visible even when matches had been found; and a folder
  whose NAME matched the keyword showed its whole content, even the
  files which did not match anything. The filter machinery is
  rewritten around a simple, uniform model:
  (1) MATCHING RULES: a file shows when its name matches; a folder
  shows when its name matches OR something matches inside it (any
  depth), so the path down to every match is visible. A
  name-matching folder does NOT bring its whole content anymore -
  its children follow the same two rules. The rules hold everywhere:
  in the scan, in the live view while it runs, in the finished
  result, in the expand fallback, and after a cancel.
  (2) LIVE VIEW: every progress tick REBUILDS the visible part of
  the tree from the worker's partial index (the old fragile
  incremental row-insertion with its sorted-position math is gone) -
  findings appear at the top level and inside every folder the user
  expanded, within one tick of being found; the rebuild carries the
  user's unfolds and the selection over, so rows only ever appear.
  The scan walks BREADTH-FIRST now, so the top level is complete
  from the very start and shallow levels fill first, where the user
  is looking. A version counter still skips idle rebuilds.
  (3) CANCEL: the x button rebuilds the tree from a cleaned snapshot
  of the partial index - everything found so far STAYS visible and
  browsable, and expands after the cancel refill exactly those rows.
  (4) EXPAND: a folder no index knows yet (the scan has not reached
  it) falls back to a cached single-level name filter - one scandir,
  the same cost as the normal expand, cached per search so the
  repeating rebuilds never re-read the disk.
  (5) The worker keeps optimistic folder rows during the walk and
  drops them in ONE final cleanup pass (the per-folder 'check'
  removal is gone); the UI never shows a folder which is not live,
  so the cleanup cannot flicker anything.
  (6) The selection carry-over works for folder nodes too now (the
  shared enum_all_sel helper can only select file nodes; the filter
  paths use their own by-path selector, which also scrolls to the
  node)
  (7) tree_on_unfold is blocked while a rebuild is filling the
  levels (the rebuild's own programmatic unfolds must not
  delete/refill what it just placed), and the unfolds the user makes
  during a search are remembered so a level which is still empty
  keeps its expanded state for the rows which come later
- note: readme.txt documents the current filter behavior (rules,
  live view, cancel, lazy expand)

- fixed #6587: the auto-unfolding of a folder during a drag&drop did not
  work at all. Two reasons:
  1. the hover state was driven by mouse-move events alone, and a cursor
     held STILL over a folder (the normal hover gesture) fires no events,
     so the 0.7s timeout could never elapse;
  2. on Windows no events existed at all during a drag: the inner
     drag&drop is the OLE 'drag_files' round-trip (no mouse events while
     it runs), and the OS file manager drag is entirely outside the
     plugin until the drop.
  The unfold-on-hover is now driven by a 100ms plugin timer over a
  "drag-hover session", fed from every event source which exists:
  tree_mouse_move (non-Windows inner drag&drop) and the new form event
  'on_drag_over' (app support: fired by the panel's OLE drop target on
  DragEnter/DragOver, (-1,-1) on DragLeave; covers the Windows inner
  drag&drop AND files dragged in from the OS file manager). The session
  is ended by mouse-up, drag-leave, any drop, and (safety net) by the
  timer itself when no mouse button is held anymore. Bonus: during the
  Windows inner drag&drop the drop target under the cursor is now
  highlighted, like the mouse-tracked inner drag&drop on other OS-es
  always did.
